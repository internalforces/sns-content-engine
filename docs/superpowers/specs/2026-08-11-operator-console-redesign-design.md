# 검토 우선형 운영 콘솔 재설계

상태: 승인됨  
작성일: 2026-08-11  
대상: FastAPI/Jinja 기반 `sns-content-engine` 운영 콘솔

## 목표

운영자가 콘솔을 열었을 때 가장 먼저 검토 대기 초안을 읽고 판단할 수 있도록 전체 화면을 재구성한다. 기존 카드형 대시보드의 시각적 소음을 제거하고, 검토 큐 중심의 편집형 워크스페이스로 바꾼다.

성공 기준은 다음과 같다.

- 첫 화면에서 가장 오래 기다린 검토 항목과 추가 확인이 필요한 항목을 바로 찾을 수 있다.
- 승인, 수정, 반려, 예약, 수동 발행 결과 기록, 스케줄러 실행의 기존 동작과 안전 장치가 유지된다.
- 잉크 블랙, 웜 아이보리, 단일 세이지 포인트만으로 정보 위계를 구분한다.
- 데스크톱, 태블릿, 모바일에서 가로 스크롤 없이 핵심 작업을 수행할 수 있다.
- 모션이 실패하거나 비활성화되어도 모든 운영 기능이 정상 작동한다.

## 현재 시스템과 변경 범위

콘솔은 FastAPI가 Jinja 템플릿을 서버 렌더링하고, `console_view_*` 모듈이 기존 워크플로와 저장소 결과를 표시용 데이터로 변환한다. 내비게이션은 `config_dir`와 `database_url` 쿼리를 모든 화면에 전달한다.

이번 변경은 다음 범위에 집중한다.

- 공통 셸, 홈, 실행 및 실패, 아티클, 검토 대기, 검토 상세, 발행 작업, 발행 상세, 스케줄러 화면의 정보 구조와 표현을 재설계한다.
- 홈 화면은 정적 안내 중심에서 검토 커맨드 센터로 변경한다.
- 필요한 경우 기존 읽기 전용 헬퍼를 조합해 홈 화면용 검토 및 상태 표시 모델을 추가한다.
- 스타일, 반응형 동작, 접근성 상태, 점진적 GSAP 모션을 추가한다.

다음은 변경하지 않는다.

- 데이터베이스 모델과 마이그레이션
- 검토 상태 전이와 승인 검증
- 드라이런 기본값과 실발행 명시 선택 규칙
- 채널별 게시 로직과 자격 증명 처리
- `config_dir`, `database_url` 운영 콘텍스트 전달 방식
- 인증 범위와 Caddy 배포 정책

## gpt-taste 프리플라이트

### 결정적 랜덤화

```text
seed = len("gpt-taste를 적용해서 운영화면을 재설계해줘") = 27
hero = "Editorial Split"; font = "Geist"
components = ["Infinite Marquee", "Horizontal Accordions", "Inline Typography Images"]
gsap = ["Scroll Pinning", "Card Stacking"]
```

승인된 미니멀 방향에 맞춰 선택된 구성 요소는 다음처럼 절제해서 사용한다.

- Editorial Split은 넓은 제목과 단일 설명/행동 영역의 비대칭으로 구현한다.
- Geist를 기본 서체로 사용하고 네트워크 폰트가 불가능하면 시스템 산세리프로 폴백한다.
- Infinite Marquee는 홈 상단에 상시 노출하지 않는다. 실행 화면의 보조 상태 스트립처럼 정보 흐름을 설명하는 곳에서만 느리게 사용한다.
- Horizontal Accordions는 검토 상세의 판단 기준 영역에만 사용한다.
- Inline Typography Images는 검토 상세나 빈 상태의 편집 이미지에만 제한하고, 홈 헤드라인은 텍스트만 유지한다.
- Scroll Pinning과 Card Stacking은 데스크톱 검토 상세에만 사용한다.

### AIDA 구조

- Navigation: 좌측 고정 내비게이션과 하단 운영 안전 상태
- Attention: “검토가 필요한 것만 남겼습니다” Editorial Split 히어로
- Interest: 우선 검토 큐와 최소 상태 요약
- Desire: 출처, 정확성, 적합성, 안전성을 순서대로 읽는 검토 상세
- Action: 가장 오래된 초안을 여는 단일 주요 CTA와 검토 결정 폼

### 히어로 검증

H1은 `max-width`가 넓은 본문 열 전체를 사용하며 `font-size: clamp(3rem, 5vw, 5.5rem)`으로 제한한다. 데스크톱은 두 줄, 모바일은 최대 세 줄을 목표로 한다. 히어로에는 스탬프 아이콘, 태그 모음, 원시 통계, 경쟁하는 다중 CTA를 넣지 않는다.

### 밀도 검증

홈의 상태 요약을 벤토로 표현하는 경우 4열 2행의 8셀을 우선 검토 큐 2×2=4셀, 검토 대기 1×1=1셀, 추가 확인 1×1=1셀, 최근 파이프라인 2×1=2셀로 정확히 채우고 `grid-auto-flow: dense`를 적용한다. 승인된 최종 방향은 더 단순한 연속형 큐를 우선하며, 사용되는 모든 격자는 빈 셀 없이 구성한다.

### 라벨과 대비

“SECTION 01”, “QUESTION 05”, “작업 01” 같은 구현 순서형 메타 라벨은 제거한다. 잉크 배경 버튼은 아이보리 텍스트, 세이지 배경 요소는 잉크 텍스트를 사용한다. 상태는 불필요한 색을 추가하지 않고 텍스트, 선, 아이콘, 굵기로 구분한다.

## 정보 구조

### 공통 셸

데스크톱은 폭 200~224px의 좌측 내비게이션과 유동형 주 작업 영역으로 나눈다. 내비게이션에는 제품명, 여섯 개 주요 화면, 현재 선택 상태, 시스템 상태, 드라이런 및 수동 검토 안내를 둔다.

태블릿과 모바일에서는 좌측 레일을 상단 헤더와 열고 닫을 수 있는 탐색 영역으로 전환한다. 현재 페이지와 핵심 안전 상태는 탐색을 열지 않아도 확인할 수 있어야 한다.

### 홈: 검토 커맨드 센터

홈은 다음 순서로 구성한다.

1. 날짜와 운영 콘텍스트를 보여주는 얇은 유틸리티 바
2. 두 줄 이내 히어로 제목, 한 문단 설명, `첫 검토 시작` 단일 주요 CTA
3. 가장 오래 기다린 순서의 우선 검토 큐
4. 검토 대기, 추가 확인 필요, 최근 파이프라인 상태의 세 가지 텍스트 요약
5. 큐가 비어 있을 때 실행 화면으로 연결하는 빈 상태

우선 검토 큐 행은 제목, 채널, 확인 사항, 대기 시간, 상세 링크만 표시한다. 본문 미리보기나 긴 설명은 상세 화면으로 이동시켜 홈의 밀도를 낮춘다.

### 검토 대기

검토 대기 페이지는 홈보다 더 많은 항목을 비교하는 작업 목록이다. 데스크톱에서는 행 기반 목록, 모바일에서는 제목을 먼저 보여주는 세로 목록을 사용한다. 계정, 채널, 생성 시각, 확인 필요 신호를 표시하며 각 행 전체가 상세 링크 역할을 한다.

### 검토 상세

검토 상세는 다음 세 영역으로 분리한다.

- 콘텐츠: 제목, 본문, 채널, 글자 수, 렌더링 결과
- 근거: 원문 URL, 출처, 브리프, 보강 상태, 감사 이력, 같은 브리프의 다른 버전
- 판단: 민감 주제 안내, 승인, 수정, 반려, 예약 또는 수동 전달 안내

데스크톱에서는 판단 기준 제목을 고정하고 근거 카드가 순차적으로 겹쳐 올라온다. 최종 결정 폼은 읽기 흐름 뒤에 배치하며, 저장되지 않은 편집 내용이 있는 상태에서 다른 결정으로 이동하지 않도록 기존 폼 동작을 명확히 표시한다.

### 실행 및 실패

최근 실행을 상단의 한 줄 요약으로 보여주고, 실행 이력과 실패를 행 기반으로 분리한다. 기술 실패와 정책상 건너뜀은 같은 색상 체계 안에서 제목과 설명으로 명확히 구분한다. 상태 색상 팔레트를 추가하지 않는다.

### 아티클

아티클은 제목과 출처를 첫 열의 핵심으로 두고, 보강 단계와 실패 사유를 보조 열로 배치한다. 긴 URL과 메시지는 줄바꿈되며 모바일에서 잘리지 않는다.

### 발행 작업과 상세

발행 작업 목록은 열린 작업을 먼저 보여준다. 상세 화면은 초안 콘텍스트, 상태 타임라인, 수동 전달 결과 폼 순으로 배치한다. 완료, 실패, 취소된 작업에서는 기존처럼 액션 폼을 숨긴다.

### 스케줄러

스케줄러는 실행할 수 있는 작업을 단순 목록으로 보여준다. 각 작업은 목적, 영향, 안전 기본값, 폼을 한 영역 안에 둔다. 실발행 체크는 별도 확인 영역에 남기고 기본 선택을 하지 않는다. 실행 결과는 같은 작업 영역 바로 아래에 표시해 원인과 결과를 떨어뜨리지 않는다.

## 시각 체계

### 색상

- Ink: `#151713`
- Warm Ivory: `#F2F0E9`
- Sage: `#738274`
- Sage Tint: `#DFE4DC`
- Neutral Rule: `#CBC9C0`

오류를 별도 빨간 카드로 만들지 않는다. 위험 또는 실패 상태는 접근 가능한 아이콘, 명확한 실패 문구, 더 굵은 경계로 표현한다. 파괴적 액션 버튼에는 필요한 범위에서만 어두운 위험 변형을 사용하되 페이지 팔레트로 확장하지 않는다.

### 타이포그래피

- 기본 서체: Geist
- H1: `clamp(3rem, 5vw, 5.5rem)`, 최대 2~3줄
- 섹션 제목: 1.5~2rem
- 본문: 0.95~1rem
- 운영 메타 정보: 0.75~0.875rem, 대문자 남용 금지

긴 한국어 제목에는 임의 줄바꿈을 넣지 않고 컨테이너 폭과 반응형 크기로 줄 수를 제어한다.

### 표면과 간격

페이지를 둥근 카드 모음으로 만들지 않는다. 큰 연속 표면, 1px 구분선, 충분한 여백으로 영역을 구분한다. 주요 장 사이에는 데스크톱 기준 96~144px, 목록 내부에는 16~24px 간격을 사용한다. 라운드는 내비게이션 활성 상태나 꼭 필요한 입력 요소에만 제한한다.

## 모션과 상호작용

GSAP과 ScrollTrigger는 점진적 향상으로 적용한다.

- 검토 상세의 판단 기준 제목을 데스크톱에서 고정한다.
- 근거 카드를 스크롤에 따라 아래에서 겹쳐 올린다.
- 실행 화면의 상태 스트립은 느린 무한 이동을 사용할 수 있지만 사용자의 주의를 끌지 않는 속도로 제한한다.
- 클릭 가능한 행은 색상 반전 대신 배경 명도 변화와 짧은 수평 이동으로 반응한다.
- 입력과 버튼은 키보드 포커스 링을 항상 제공한다.

`prefers-reduced-motion: reduce`에서는 고정, 스크럽, 스택, 무한 이동을 모두 해제한다. GSAP을 불러오지 못해도 문서 순서와 폼은 그대로 사용 가능해야 한다.

## 데이터 흐름과 컴포넌트 경계

서버는 계속 완전한 HTML을 제공한다.

1. 라우트가 현재 운영 콘텍스트를 해석한다.
2. 기존 워크플로 조회 헬퍼가 실행, 아티클, 검토, 발행 데이터를 읽는다.
3. `console_view_*` 변환기가 템플릿 전용 표시 모델을 만든다.
4. Jinja 템플릿이 공통 셸과 페이지별 영역을 렌더링한다.
5. CSS와 작은 JavaScript 모듈이 반응형 탐색, GSAP 모션, 점진적 상호작용만 담당한다.
6. 상태 변경 폼은 기존 FastAPI POST 경로와 리다이렉트 흐름을 사용한다.

구현 단위는 공통 셸, 내비게이션, 히어로, 검토 큐, 상태 요약, 데이터 목록, 피드백, 폼 액션, 검토 상세 근거 영역으로 나눈다. 반복 구조는 Jinja 매크로나 포함 템플릿을 사용해 화면 간 마크업 차이를 줄인다.

## 오류와 빈 상태

- 데이터가 없으면 단순히 “0”만 표시하지 않고 다음 가능한 작업으로 연결한다.
- 조회 실패는 기존 서버 오류 처리 규칙을 유지하되, 사용자에게 현재 콘텍스트와 복구 가능한 다음 행동을 알려준다.
- 폼 검증 오류는 제출한 폼 바로 위에 표시하고 입력값을 유지한다.
- 성공 메시지는 관련 결과와 가까운 위치에 표시한다.
- 긴 오류 코드와 URL은 `overflow-wrap: anywhere`로 컨테이너를 벗어나지 않는다.
- 모션 또는 폰트 로드 실패는 기능 실패로 이어지지 않는다.

## 접근성과 반응형

- 모든 링크와 버튼은 44px에 가까운 조작 영역을 확보한다.
- 현재 내비게이션은 색상 외에 굵기와 위치로도 구분한다.
- 표 헤더와 행 연결을 유지하고 모바일 변환 시 각 값의 라벨을 제공한다.
- 포커스 순서는 시각 순서와 일치한다.
- 키보드로 탐색, 검토 상세 진입, 폼 제출이 가능해야 한다.
- 375px, 768px, 1440px에서 레이아웃을 검증한다.
- 전체 셸은 `overflow-x: hidden; width: 100%; max-width: 100%`를 유지한다.

## 테스트 전략

### 자동 테스트

- 기존 `tests/test_console.py`의 문구 및 동작 회귀 테스트를 유지하거나 새 정보 구조에 맞게 의도를 보존하여 갱신한다.
- 홈이 검토 큐와 상태 요약의 데이터 있음/없음 상태를 렌더링하는 테스트를 추가한다.
- 모든 내비게이션 링크가 운영 콘텍스트 쿼리를 유지하는지 검증한다.
- 승인, 수정, 반려, 예약, 수동 전달, 스케줄러 POST 동작의 기존 테스트를 유지한다.
- 정적 CSS와 JavaScript 자산이 제공되는지 검증한다.

### 시각 및 수동 검증

- 375px, 768px, 1440px 스크린샷 비교
- 가로 스크롤 부재
- 키보드 탐색과 포커스 표시
- 축소 모션 설정에서 애니메이션 제거
- JavaScript 차단 상태에서 링크와 폼 작동
- 긴 한국어 제목, URL, 오류 메시지의 줄바꿈
- 빈 데이터, 일부 실패, 많은 검토 항목 상태

## 완료 조건

- 첫 화면이 승인된 미니멀 검토 워크스페이스 구조와 색상 체계를 따른다.
- 모든 주요 콘솔 화면이 같은 셸, 타이포그래피, 선 기반 목록, 폼 규칙을 사용한다.
- 기존 운영 기능과 안전 기본값이 유지된다.
- 검토 상세에만 제한된 GSAP ScrollTrigger 모션이 적용되고 축소 모션 폴백이 있다.
- 기존 테스트와 새 회귀 테스트가 통과한다.
- 지원 화면 너비에서 가로 스크롤과 잘린 조작 요소가 없다.
